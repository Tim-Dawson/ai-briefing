AWS Certified Solutions Architect - Associate (SAA-C03) Revision Guide

June 16th, 2026 9 min read

At a Glance

  • Exam shape: 65 questions total, with 50 scored and 15 unscored. Passing score is 720/1000.
  • Question types: multiple choice and multiple response. There is no penalty for guessing.
  • Official domain weighting: Secure Architectures 30%, Resilient Architectures 26%, High-Performing Architectures 24%, Cost-Optimized Architectures 20%.
  • If you are short on time: prioritise IAM, VPC, S3, EC2, ELB, Auto Scaling, Route 53, RDS/Aurora, DynamoDB, SQS/SNS/EventBridge, Lambda, CloudFront, KMS, and disaster recovery patterns.
  • Mental model: AWS loves answers that are managed, scalable, multi-AZ, least-privilege, decoupled, and operationally simple.

What the exam is really testing

The SAA-C03 exam is less about memorising every service in existence and more about choosing the best architecture for a business requirement. Most questions are variants of:

If two answers both work, AWS usually wants the one that is:

  • Which design is secure enough without being overcomplicated?
  • Which design is resilient across failures?
  • Which service is the best fit for this access pattern?
  • Which option is the most cost-effective while still meeting requirements?
  • more managed
  • easier to operate
  • more fault tolerant
  • better aligned to the stated requirement

1. Design Secure Architectures

Know cold:

High-yield reminders:

  • Design secure access to AWS resources
  • Design secure workloads and applications
  • Determine appropriate data security controls
  • IAM users vs roles vs groups vs policies
  • cross-account access with STS AssumeRole
  • IAM Identity Center and federation
  • root user protection and MFA
  • resource policies vs identity policies
  • KMS for encryption at rest
  • ACM/TLS for encryption in transit
  • security groups vs network ACLs
  • Secrets Manager vs Parameter Store
  • WAF vs Shield
  • private vs public subnets, NAT gateway, VPC endpoints
  • Security groups are stateful; NACLs are stateless.
  • Put databases in private subnets.
  • Use roles, not hardcoded keys in apps.
  • Use VPC endpoints to keep traffic to AWS services off the public internet where possible.
  • Use KMS CMKs/keys and key policies when access to encrypted data is part of the question.
  • Use Secrets Manager when automatic secret rotation matters.

2. Design Resilient Architectures

Know cold:

High-yield reminders:

  • Design scalable and loosely coupled architectures
  • Design highly available and/or fault-tolerant architectures
  • SQS, SNS, EventBridge
  • Auto Scaling
  • ALB/NLB
  • multi-AZ vs multi-Region
  • Route 53 routing and health checks
  • disaster recovery patterns: backup/restore, pilot light, warm standby, active-active
  • RPO and RTO
  • stateless design
  • immutable infrastructure
  • SQS decouples producers and consumers.
  • SNS is pub/sub fan-out.
  • EventBridge is event routing between services and apps.
  • Step Functions are for workflow orchestration.
  • If the requirement says absorb bursts, think queueing.
  • If the requirement says high availability, think multi-AZ first.
  • If it says survive regional failure, think multi-Region.

3. Design High-Performing Architectures

Know cold:

High-yield reminders:

  • Determine storage solutions
  • Design compute solutions
  • Determine database solutions
  • Determine network architectures
  • Determine data ingestion/transformation solutions
  • S3 vs EBS vs EFS
  • EC2 instance families and Auto Scaling
  • Lambda sizing and concurrency basics
  • RDS vs Aurora vs DynamoDB
  • ElastiCache
  • CloudFront and Global Accelerator
  • Direct Connect, VPN, PrivateLink
  • Kinesis, Glue, Athena, EMR
  • S3 = object storage, massively scalable, not a mounted OS disk.
  • EBS = block storage for one EC2 instance at a time in one AZ.
  • EFS = shared file storage across multiple instances.
  • Aurora is usually the “better managed, higher-performance relational” answer.
  • DynamoDB is for key-value/document workloads needing massive scale and low latency.
  • ElastiCache helps with read-heavy and latency-sensitive workloads.
  • CloudFront improves global content delivery and can reduce origin load.

4. Design Cost-Optimized Architectures

Know cold:

High-yield reminders:

  • Design cost-optimized storage solutions
  • Design cost-optimized compute solutions
  • Design cost-optimized database solutions
  • Design cost-optimized network architectures
  • S3 lifecycle policies and storage classes
  • Savings Plans, Reserved Instances, Spot
  • right-sizing
  • NAT gateway trade-offs
  • data transfer costs
  • read replicas and caching as cost/performance levers
  • cost tools: Cost Explorer, Budgets, CUR
  • Use Spot for fault-tolerant, interruptible workloads.
  • Use Savings Plans/Reserved when usage is steady.
  • Use S3 lifecycle policies aggressively for colder data.
  • Watch for cross-AZ and cross-Region transfer charges.
  • Sometimes a “cheaper” option is wrong if it fails the availability requirement.

Compute

Rule of thumb:

  • EC2: maximum control, legacy apps, special OS/runtime needs, predictable long-running workloads.
  • Lambda: event-driven, bursty, short-lived, no server management.
  • ECS with Fargate: containers without managing servers.
  • EKS: Kubernetes when you specifically need Kubernetes.
  • Batch: scheduled or queued batch compute.
  • If the question does not require server control, AWS often prefers Lambda or Fargate over raw EC2.

Load balancing

  • ALB: HTTP/HTTPS, Layer 7, path-based or host-based routing.
  • NLB: very high performance, TCP/UDP, static IPs, lower-level traffic.
  • Gateway Load Balancer: appliance insertion.

Storage

  • S3: durable object storage, static assets, backups, data lakes, logs.
  • EBS: block storage for EC2, databases, boot volumes.
  • EFS: shared POSIX file system for Linux workloads.
  • FSx: specialised managed file systems for Windows, Lustre, NetApp, OpenZFS.

Databases

  • RDS: managed relational databases.
  • Aurora: high-performance managed relational, common “best answer” for relational HA/performance.
  • DynamoDB: serverless NoSQL at scale.
  • Redshift: analytics warehouse.
  • ElastiCache: cache, not primary durable database.

Messaging and integration

  • SQS: queue, buffering, decoupling.
  • SNS: push fan-out notifications.
  • EventBridge: event bus and rule-based routing.
  • Step Functions: orchestrated workflows.

Networking

  • Route 53: DNS, health checks, routing policies.
  • CloudFront: CDN and edge caching.
  • Global Accelerator: static anycast IPs and improved global routing for TCP/UDP applications.
  • Direct Connect: dedicated private connectivity.
  • Site-to-Site VPN: faster/cheaper setup than DX, but internet-based.
  • PrivateLink: private service access without traversing public internet.

S3 vs EBS vs EFS

  • Need an object store for files, backups, logs, or static website assets: S3
  • Need a boot disk or low-latency block device for one EC2 instance: EBS
  • Need a shared filesystem mounted by many Linux instances: EFS

RDS vs Aurora vs DynamoDB

  • Need SQL and a standard relational engine: RDS
  • Need SQL with stronger managed HA/performance and AWS-native clustering: Aurora
  • Need huge scale, millisecond latency, flexible key-value/document model: DynamoDB

SQS vs SNS vs EventBridge

  • Need messages processed later by workers: SQS
  • Need one message fan out to many subscribers: SNS
  • Need event routing based on rules between systems/services: EventBridge

CloudFront vs Global Accelerator

  • Need caching for web/static/dynamic content: CloudFront
  • Need better global routing and static IPs for non-cache-centric applications: Global Accelerator

Secrets Manager vs Systems Manager Parameter Store

  • Need secret rotation and secret-specific management: Secrets Manager
  • Need simpler configuration values and parameters, sometimes at lower cost: Parameter Store

Disaster recovery patterns

Know these in order of increasing cost and decreasing recovery time:

Exam trick:

  • Backup and restore: cheapest, slowest recovery
  • Pilot light: critical core always on, rest started during failover
  • Warm standby: scaled-down but running environment in another Region
  • Active-active: highest cost, fastest recovery, both environments live
  • If the question gives strict RTO/RPO, use that to eliminate half the answers immediately.

Security patterns AWS likes

Watch for these traps:

  • least privilege everywhere
  • MFA for privileged access
  • roles instead of long-term access keys
  • encryption at rest and in transit
  • private subnets for private resources
  • security groups as primary instance-level control
  • logging and visibility through CloudTrail/CloudWatch-style thinking
  • managed secrets rather than plaintext credentials
  • giving the root account day-to-day responsibilities
  • storing credentials in code or on EC2 instances
  • placing a database in a public subnet
  • choosing a NAT gateway when a gateway endpoint for S3 or DynamoDB would be cleaner and cheaper

Cost traps and optimisation patterns

  • Data transfer can quietly dominate costs.
  • NAT gateways are convenient but not free.
  • Cross-AZ traffic may matter in chatty architectures.
  • S3 Intelligent-Tiering and lifecycle rules are favourite answers for changing access patterns.
  • Graviton instance families can be a cost/performance win if compatibility allows.
  • Reserved capacity options are attractive only when utilisation is predictable enough.

How to answer architecture questions faster

1. Read the last sentence first. It usually tells you what success means.

2. Underline the hard requirement: cheapest, fastest, lowest ops, multi-Region, private, near-real-time, and so on.

3. Eliminate answers that violate one explicit requirement, even if they sound clever.

4. Prefer managed services unless the question gives a reason not to.

5. If a service solves the problem natively, AWS usually wants that over a handmade EC2 contraption.

Last-minute cram checklist

  • IAM policy evaluation basics
  • security groups vs NACLs
  • public vs private subnet design
  • NAT gateway, internet gateway, VPC endpoints
  • S3 storage classes and lifecycle rules
  • EC2 purchasing options
  • ALB vs NLB
  • Auto Scaling basics
  • SQS vs SNS vs EventBridge
  • RDS Multi-AZ vs read replicas
  • Aurora vs RDS vs DynamoDB
  • Route 53 routing policies
  • CloudFront use cases
  • KMS, ACM, Secrets Manager
  • DR patterns with RTO/RPO

One Thing to Dig Into Before Friday

If you only do one focused review session, make it a service-comparison drill. Most wrong answers on SAA-C03 come from picking a service that is plausible but not the best fit. Spend 30 to 45 minutes forcing yourself through comparisons like SQS vs SNS vs EventBridge, RDS vs Aurora vs DynamoDB, S3 vs EBS vs EFS, ALB vs NLB, and Multi-AZ vs read replica.

Suggested final 3-day plan

  • Tuesday: security + networking + IAM + VPC foundations
  • Wednesday: resilience + messaging + disaster recovery + Route 53
  • Thursday: databases + storage + cost optimisation + service comparisons
  • Friday morning: light review only, especially comparison tables and common traps
