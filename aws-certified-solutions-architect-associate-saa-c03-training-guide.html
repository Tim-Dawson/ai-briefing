AWS Certified Solutions Architect - Associate (SAA-C03) Training Guide

June 16th, 2026 17 min read

At a Glance

  • Exam shape: 65 questions in 130 minutes. AWS says 50 are scored and 15 are unscored, and the passing score is 720/1000.
  • What you are really being tested on: choosing the best architecture, not just a possible one.
  • The four domains: Secure Architectures 30%, Resilient Architectures 26%, High-Performing Architectures 24%, Cost-Optimized Architectures 20%.
  • What AWS usually prefers: managed services, least privilege, multi-AZ, decoupling, autoscaling, and designs that reduce operational effort.
  • Most important services to know well: IAM, VPC, EC2, Auto Scaling, ELB, S3, CloudFront, Route 53, RDS/Aurora, DynamoDB, EFS/EBS, Lambda, SQS, SNS, EventBridge, KMS, WAF, Shield, ElastiCache, API Gateway.
  • Fast exam rule: if two answers both work, AWS usually wants the one that is more managed, more resilient, and simpler to operate.

How to Think Like the Exam

The SAA-C03 is mostly a design exam. AWS gives you a business problem, then asks which solution is the best fit. That means you need to think in trade-offs:

The exam loves answers that reduce human babysitting. If an answer uses a managed service and still meets the requirement, it usually beats an answer that needs custom servers, cron jobs, or home-grown patchwork. AWS is many things, but sentimental about hand-maintained infrastructure is not one of them.

  • Is the workload stateful or stateless?
  • Does it need low latency, high throughput, durability, or cheap storage?
  • Does it need to survive an instance failure, an Availability Zone failure, or a Region failure?
  • Is the priority security, availability, performance, or cost?

What the Question Is Usually Really Asking

Most scenario questions hide the real requirement in the last line. Read that line first.

Typical hidden asks:

  • “Most cost-effective” means remove waste, but still meet the requirement.
  • “Operational overhead must be minimal” means prefer serverless or managed.
  • “Highly available” usually means multi-AZ.
  • “Disaster recovery across Regions” means multi-Region or a DR pattern.
  • “Decouple components” means add SQS, SNS, or EventBridge.
  • “Store files durably and cheaply” means S3, not EBS.
  • “Shared filesystem across many servers” means EFS.
  • “Low-latency key-value lookups at huge scale” means DynamoDB.

Stateless Web App Pattern

This is one of the most common mental models on the exam:

Why AWS likes this:

If the question describes a web application that must scale during traffic spikes, this pattern is often the baseline answer.

  • users hit Route 53
  • traffic goes to CloudFront or directly to an Application Load Balancer
  • requests go to EC2 instances in an Auto Scaling group across multiple AZs
  • application state is not stored on the instance itself
  • shared session state, if needed, goes into ElastiCache or a database
  • files go to S3
  • relational data goes to RDS/Aurora
  • instances can die and be replaced
  • scaling is easy
  • multi-AZ improves availability
  • storage is separated from compute

Event-Driven / Serverless Pattern

Common version:

Why it is chosen:

Use this when the question mentions unpredictable spikes, minimal ops, or event-based processing.

  • users upload files to S3
  • S3 triggers Lambda
  • Lambda processes the file
  • results go to DynamoDB, S3, or another service
  • notifications go out through SNS or events through EventBridge
  • no servers to manage
  • good for bursty or irregular workloads
  • scales automatically
  • you only pay when it runs

Decoupled Worker Pattern

Classic design:

This is the answer when the system needs to absorb bursts without overwhelming the backend.

Example:

Keyword clues:

  • frontend or producer writes jobs into SQS
  • worker fleet reads from the queue
  • workers scale independently
  • failures do not lose requests if messages remain in the queue
  • an ecommerce site receives 20,000 order-related events in a sudden spike
  • instead of sending them directly to a processing service that melts under pressure, put them on SQS
  • worker instances or Lambda functions process at a controlled rate
  • “buffer”
  • “smooth spikes”
  • “decouple”
  • “process asynchronously”

IAM Users, Groups, Roles, and Policies

High-yield rule:

Example:

  • User: identity for a person or application when long-term credentials are required
  • Group: collection of users with shared permissions
  • Role: temporary identity that can be assumed; heavily preferred for workloads
  • Policy: JSON document defining permissions
  • For applications running on AWS, prefer IAM roles over access keys.
  • An EC2 instance needs to read from S3.
  • Good answer: attach an IAM role to the EC2 instance.
  • Bad answer: store access keys in a config file on the instance.

Identity-Based Policies vs Resource-Based Policies

Bucket policies commonly appear in cross-account access questions.

Example:

  • Identity-based policy: attached to a user, group, or role
  • Resource-based policy: attached to the resource itself, such as an S3 bucket policy
  • Account A needs an app in Account B to write to an S3 bucket.
  • You may need a role in Account B and a bucket policy in Account A allowing that role.

Least Privilege

AWS loves least privilege. If an answer gives broad admin access when narrow permissions would work, it is probably wrong.

Security Groups vs Network ACLs

Remember:

AWS usually expects you to use security groups as the main instance-level control.

  • Security groups: stateful, attached to instances/ENIs, allow rules only
  • NACLs: stateless, attached to subnets, allow and deny rules
  • if inbound traffic is allowed by a security group, the response is automatically allowed back out
  • NACLs require explicit handling because they are stateless

Encryption at Rest and In Transit

Example:

  • At rest: think KMS, SSE-S3, SSE-KMS, encrypted EBS, encrypted RDS, encrypted snapshots
  • In transit: think TLS, HTTPS, ACM certificates
  • A company stores sensitive documents in S3 and wants audit-friendly key control.
  • Best answer: use SSE-KMS with the right key policy.

Secrets Manager vs Parameter Store

If the question explicitly mentions automatic rotation, choose Secrets Manager.

  • Secrets Manager: for passwords, API keys, database credentials, and automatic rotation
  • Parameter Store: for configuration values, and sometimes secrets, usually with simpler requirements

WAF, Shield, and Firewall-ish Thinking

If the question is about SQL injection, XSS, or filtering bad web traffic, think WAF.

  • AWS WAF: filters HTTP/S requests, blocks common web exploits
  • AWS Shield Standard: built-in DDoS protection
  • Shield Advanced: extra protection and support for serious DDoS cases

Public vs Private Subnets

Common design:

If an exam answer puts a database in a public subnet for no good reason, it is usually bait.

  • Public subnet: route to an internet gateway
  • Private subnet: no direct internet route
  • ALB in public subnets
  • app servers in private subnets
  • database in private subnets

Internet Gateway, NAT Gateway, and VPC Endpoints

Very common trap:

  • Internet Gateway: lets public subnet resources reach the internet
  • NAT Gateway: lets private subnet resources initiate outbound internet access
  • VPC Endpoint: private access to AWS services without using the public internet
  • If private instances need to access S3 or DynamoDB, a gateway endpoint may be cheaper and more secure than routing through a NAT Gateway.

Route 53

Know the routing basics:

Example:

  • Simple routing: single resource
  • Weighted routing: distribute traffic by percentage
  • Latency routing: lowest latency Region
  • Failover routing: active-passive using health checks
  • Geolocation/geoproximity: location-based traffic steering
  • You have a primary site in `eu-west-1` and a DR site in `eu-central-1`.
  • If traffic should switch only when the primary fails, use failover routing with health checks.

CloudFront vs Global Accelerator

Use CloudFront when caching content helps.

Use Global Accelerator when the app needs globally improved routing but caching is not the main point.

  • CloudFront: CDN, caching, edge delivery for content
  • Global Accelerator: static anycast IPs and better network pathing for global TCP/UDP applications

EC2

Choose EC2 when you need:

But remember: EC2 is rarely the “minimal operational overhead” answer.

  • full OS control
  • custom software
  • unusual runtimes
  • long-running workloads
  • predictable steady compute

Auto Scaling

Auto Scaling adds or removes EC2 instances based on demand or schedule.

Good for:

A common correct architecture is:

  • handling traffic spikes
  • improving availability
  • replacing unhealthy instances
  • ALB + Auto Scaling group across at least two AZs

Lambda

Lambda is for short-lived, event-driven compute.

Use it when:

Watch the fit:

  • traffic is spiky or unpredictable
  • the task responds to events
  • you want no server management
  • Lambda is excellent for image processing, API backends, and event triggers
  • less ideal for long-running, stateful, or highly customised server processes

ECS, Fargate, and EKS

Exam rule:

  • ECS: AWS-native container orchestration
  • Fargate: run containers without managing servers
  • EKS: managed Kubernetes
  • If the requirement is just “run containers with minimal ops,” ECS on Fargate is often better than EKS.
  • Choose EKS only when the question specifically needs Kubernetes.

S3

S3 is object storage. It is massively durable and scales very well.

Use S3 for:

Do not treat S3 like a normal mounted disk for an application server.

Important features:

Example:

  • static website assets
  • backups
  • logs
  • media files
  • archived data
  • data lakes
  • versioning
  • lifecycle rules
  • cross-Region replication
  • storage classes
  • event notifications
  • A company stores millions of infrequently accessed documents and wants low cost with automatic archival.
  • Think S3 lifecycle policies to transition data to colder storage classes.

EBS

EBS is block storage for EC2.

Use it for:

High-yield fact:

  • boot volumes
  • transactional databases on EC2
  • low-latency disks attached to an instance
  • An EBS volume is tied to a single AZ.

EFS

EFS is a shared managed file system for Linux.

Use it when:

Exam clue:

  • multiple EC2 instances need the same files
  • the application expects a normal file system
  • the storage must scale automatically
  • If many app servers need access to the same uploaded files, EFS is often the answer.

RDS

RDS is managed relational database hosting for engines like MySQL and PostgreSQL.

Use it when:

  • you need SQL
  • you need joins and transactions
  • you want management features without running the database yourself

Aurora

Aurora is AWS’s higher-performance managed relational option.

It appears a lot because it is:

If the question wants relational plus high performance plus easier ops, Aurora is often the answer.

  • managed
  • highly available
  • performant
  • strong for many production relational workloads

DynamoDB

DynamoDB is managed NoSQL key-value/document storage.

Use it when:

Typical exam fit:

Do not pick DynamoDB just because it sounds modern. If the workload clearly needs heavy relational joins, SQL is the better fit.

  • you need single-digit millisecond latency
  • the access pattern is known
  • scale may become massive
  • schema flexibility is helpful
  • user profile lookups
  • session stores
  • shopping cart state
  • IoT event metadata

ElastiCache

ElastiCache improves performance by caching data in memory.

Use it when:

If the question says “reduce load on the database and improve response time for frequently requested data,” think ElastiCache.

  • reads are heavy
  • database load is high
  • latency matters
  • session data needs fast access

SQS

SQS is a queue. It stores messages until consumers process them.

Use it for:

Example:

  • decoupling services
  • buffering bursts
  • asynchronous processing
  • an image upload service should not fail just because the thumbnail generator is busy
  • store the processing task in SQS

SNS

SNS is pub/sub fan-out.

Use it when one event must notify many subscribers.

Example:

SNS can push to multiple endpoints at once.

  • order placed
  • email service, analytics pipeline, and fraud detector all need the event

EventBridge

EventBridge is an event bus with routing rules.

Use it when:

Simple memory trick:

  • services publish events
  • consumers need to react based on event patterns
  • you want cleaner event-driven integration
  • SQS stores work
  • SNS broadcasts messages
  • EventBridge routes events

Step Functions

Step Functions orchestrates multi-step workflows.

Use it when a process has:

If the question is about coordinating several Lambda functions in order, Step Functions is often correct.

  • multiple steps
  • branching logic
  • retries
  • timeouts
  • human-readable state tracking

Multi-AZ vs Multi-Region

Do not overbuild:

  • Multi-AZ: protects against an AZ failure
  • Multi-Region: protects against a full Region failure and can reduce latency for global users
  • if the requirement is simply “high availability,” multi-AZ is often enough
  • if it explicitly says “survive a regional outage,” you need multi-Region thinking

RTO and RPO

Exam trick:

If a company can tolerate hours of downtime and some data loss, backup and restore may be enough.

If downtime must be minutes and near-zero data loss, you need a stronger DR pattern.

  • RTO: how quickly you must recover
  • RPO: how much data loss is acceptable
  • smaller RTO and smaller RPO usually mean higher cost

Disaster Recovery Patterns

From cheapest/slowest to most expensive/fastest:

Example:

  • Backup and restore
  • Pilot light
  • Warm standby
  • Active-active
  • A startup needs a DR plan but can tolerate several hours of recovery.
  • Best answer may be backups plus infrastructure templates, not a full second live environment.

Choose the Right Storage for the Access Pattern

This is a classic source of exam questions.

  • need object storage: S3
  • need block storage for one server: EBS
  • need shared file storage: EFS

Choose the Right Database for the Query Pattern

  • relational and transactions: RDS/Aurora
  • key-value at huge scale: DynamoDB
  • analytics warehouse: Redshift
  • cache hot data: ElastiCache

Caching

Two common cache answers:

Example:

  • CloudFront for content near end users
  • ElastiCache for data/app caching near your compute
  • A global media site serves the same images repeatedly.
  • CloudFront reduces latency and offloads the origin.

EC2 Pricing Models

Use Spot when workloads are:

Bad Spot use case:

  • On-Demand: flexible, no commitment
  • Reserved Instances / Savings Plans: cheaper for steady usage
  • Spot Instances: cheapest, but can be interrupted
  • fault tolerant
  • interruptible
  • batch-like
  • a critical single-instance production database

S3 Cost Optimisation

Know the big levers:

  • storage classes
  • lifecycle policies
  • intelligent tiering
  • deleting unneeded versions or incomplete uploads when appropriate

Network Cost Traps

Watch for:

Very exam-like pattern:

  • NAT Gateway charges
  • cross-AZ traffic
  • cross-Region replication costs
  • internet egress
  • private instances need S3 access
  • cheapest secure design may be a VPC gateway endpoint instead of NAT traversal

S3 vs EBS vs EFS

  • S3: object storage for files, backups, logs, static content
  • EBS: block storage for one EC2 instance in one AZ
  • EFS: shared file system for multiple Linux instances

RDS vs Aurora vs DynamoDB

  • RDS: managed relational DB
  • Aurora: stronger AWS-native managed relational choice, often higher performance
  • DynamoDB: NoSQL at massive scale with very low latency

ALB vs NLB

  • ALB: HTTP/HTTPS, path-based routing, host-based routing, Layer 7 features
  • NLB: TCP/UDP, very high performance, static IPs

NAT Gateway vs VPC Endpoint

  • NAT Gateway: outbound internet from private subnets
  • VPC Endpoint: private access to supported AWS services

SNS vs SQS

  • SNS: many subscribers receive the message
  • SQS: one consumer processes work from the queue

Scenario 1: Sudden Traffic Spikes

An online store has unpredictable traffic bursts during flash sales. The application is a web tier talking to a relational database. The business wants high availability and minimal manual scaling.

What you should think:

Why this is right:

  • web tier should be stateless
  • use ALB + Auto Scaling group across multiple AZs
  • database should be RDS/Aurora Multi-AZ
  • static assets should go to S3, possibly with CloudFront
  • it scales automatically
  • it avoids single points of failure
  • it uses managed components

Scenario 2: Backend Falls Over During Peak Uploads

A photo app receives massive evening upload spikes. Image processing does not need to happen instantly, but uploads must succeed.

What you should think:

Why:

  • store uploads in S3
  • trigger processing asynchronously or queue work in SQS
  • process with Lambda or scalable workers
  • uploads are accepted even when processing is busy
  • the queue absorbs bursts

Scenario 3: Private Instances Need S3 Access

Application servers are in private subnets. They must read files from S3. The company wants to minimise cost and keep traffic off the public internet.

Correct instinct:

Why not NAT?

  • use an S3 gateway VPC endpoint
  • NAT would work, but it is more expensive and less elegant for this requirement

Scenario 4: Shared Files Across Many App Servers

Several EC2 instances process the same shared content and need simultaneous filesystem access.

Correct answer:

Not:

  • EFS
  • S3, because it is object storage
  • EBS, because it is not the right shared multi-instance file system answer

Scenario 5: Global Performance for Static Content

A company serves images and videos to users around the world and wants lower latency and reduced load on the origin.

Correct answer:

Why:

  • CloudFront
  • caches content at edge locations
  • improves performance for global users

Traps That Catch People

  • Choosing multi-Region when the requirement only asked for high availability. That adds cost and complexity.
  • Choosing EC2 when the question clearly wants minimal operational overhead.
  • Choosing DynamoDB for a workload that plainly needs relational joins and SQL.
  • Forgetting that security groups are stateful and NACLs are stateless.
  • Using NAT Gateway for S3 access when a VPC endpoint is better.
  • Treating S3 like a normal mounted server disk.
  • Using long-term IAM access keys when a role is available.

Day 1: Core Service Mastery

Memorise the purpose and decision points for:

  • IAM, roles, policies, KMS, security groups, NACLs
  • VPC, subnets, NAT, endpoints, Route 53, CloudFront
  • EC2, Auto Scaling, ALB, Lambda, ECS/Fargate
  • S3, EBS, EFS
  • RDS, Aurora, DynamoDB, ElastiCache
  • SQS, SNS, EventBridge, Step Functions

Day 2: Scenario Practice

Do not just reread notes. Practice thinking in architectures:

  • identify the real requirement
  • remove answers that do not meet security, resilience, or cost needs
  • prefer managed services when possible
  • ask what fails if one instance or one AZ dies
  • ask whether the answer decouples the system or creates a bottleneck

Night-Before Memory Pegs

If you remember nothing else, remember these:

  • S3 for object storage
  • EBS for one instance’s block storage
  • EFS for shared file storage
  • RDS/Aurora for relational
  • DynamoDB for low-latency NoSQL at scale
  • SQS to decouple and buffer
  • SNS to fan out
  • EventBridge to route events
  • ALB + Auto Scaling + multi-AZ for scalable web apps
  • Lambda for event-driven, short-lived compute
  • Roles, not access keys
  • Private subnets for databases
  • KMS for encryption control
  • CloudFront for global content delivery
  • VPC endpoints for private access to AWS services

One Thing to Drill Before Friday

Spend your final revision block on service selection by scenario, not raw memorisation.

The people who pass comfortably are not the ones who can recite 200 product names like a frightened catalogue. They are the ones who can look at a problem and say:

That is the real exam skill.

  • this needs decoupling, so use SQS
  • this needs shared storage, so use EFS
  • this needs cheap durable objects, so use S3
  • this needs relational HA, so use Aurora or RDS Multi-AZ
  • this needs lower ops, so stop lovingly handcrafting EC2 for everything
